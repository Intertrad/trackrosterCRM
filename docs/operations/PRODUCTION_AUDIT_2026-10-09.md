# TrackRoster full-stack production audit

**Audit date:** 2026-10-09  
**Audited branch:** `dev-v2`  
**Audited commit:** `5a0b4ad` (`ci: test dev-v2 before production`)  
**Scope:** monorepo source, API, web application, worker, database/migrations,
CI, deployment documentation, error handling, and production-readiness evidence.

This is an evidence-based audit. It does not claim that a provider, DNS record,
secret, managed database, queue, or browser session is healthy when that resource
was not available to this checkout. No production data or credentials were
changed during this audit.

## Executive assessment

The repository has a strong application test base and the local quality gates are
green, but it is not ready for an unconditional production release. The initial
audit run on commit `5a0b4ad` was red: 57 of 58 API integration files passed
(612 of 613 tests), while the map scope-limit test timed out after 90 seconds.
The follow-up run on documentation commit `2bf0b40` passed all 58 integration
files (613 tests) and the build in 6m48s. The timeout remains a fragile test
signal that should be made deterministic before it becomes a recurring release
blocker.

The most important release risks are:

1. the failing/slow map integration path is a release gate;
2. production deployment configuration is not reproducible from the repository;
3. browser/API error handling is only partially standardized and lacks structured
   field details;
4. failed account-mail delivery has no operator alert or readiness signal;
5. security headers and CORS are not configured in the application bootstrap and
   are therefore dependent on an unverified external proxy;
6. backup scheduling, provider-backed restore, and staging browser E2E remain
   unverified.

## Findings

### AUD-001 — P0 release blocker: map integration test exceeds the CI time budget

**Category:** Reliability / performance / CI  
**Location:** `apps/api/test/maps.integration.spec.ts:366-405`  
**Evidence:** CI run `37904813545` passed 57/58 integration files and 612/613
tests. The test `rejects oversized visible scopes while applying ownership before
the size limit` timed out after 90,000 ms. It inserts 20,001 establishments and
campaign memberships before exercising the 20,000-row guard in
`apps/api/src/maps/map.service.ts:16-92`.

**Impact:** Every `dev-v2` push is prevented from reaching the build gate. A
release can appear functionally healthy while the required production gate is
red. The fixture also masks whether the query itself is bounded under realistic
large scopes.

**Current behavior:** The test is intentionally bounded to 90 seconds, but the
fixture setup and cleanup can exceed that budget in GitHub-hosted Postgres.

**Expected behavior:** The test should deterministically exercise the limit within
the CI budget, and the production query should remain bounded and indexed.

**Recommendation:** Replace the 20,001-row insert with a deterministic database
fixture or a lower-cost query-plan assertion that still proves ownership is
applied before the limit. Measure `EXPLAIN (ANALYZE, BUFFERS)` on a representative
dataset, then add a separate load test for the full-size scope. Do not merely
increase the timeout without measuring the query.

**Status:** Mitigated for this run; keep open as a P1 test-determinism item until
the fixture is made consistently bounded.

### AUD-002 — P1: production deployment is not reproducible from the repository

**Category:** Release engineering / operations  
**Location:** repository root; `README.md:151-154`; `docs/operations/DEPLOYMENT.md`  
**Evidence:** No `render.yaml`, `vercel.json`, deployment workflow, Terraform,
or equivalent production target manifest was found. README says the production
hosting provider is still to be finalized, while the product brief assumes a
Vercel/Render deployment.

**Impact:** Reviewers cannot verify API/web/worker version alignment, runtime
commands, migrations, health probes, rollback behavior, or required environment
variables from Git. A deployment can drift from the audited commit.

**Expected behavior:** A release commit should identify the exact web, API,
worker, database migration, Redis, object storage, mail, and health-check
configuration used in production.

**Recommendation:** Add provider manifests or an infrastructure repository link,
an environment-variable schema with secret names only, a release runbook, and a
rollback procedure. Keep secret values in the provider secret manager.

**Status:** Open; needs an architecture/deployment decision.

### AUD-003 — P1: API error envelopes are not sufficiently structured for a shared UI contract

**Category:** API contract / frontend error handling  
**Location:** `apps/api/src/errors/api-exception.filter.ts:84-124`,
`apps/api/src/errors/api-error.types.ts:1-14`,
`apps/web/src/lib/api/api-error.ts`  
**Evidence:** The global filter returns `statusCode`, `code`, `message`,
`error`, and `requestId`. Validation messages can be an array of strings, but
there is no stable `details`/field map or explicit success discriminator. Many
services still throw free-form strings, so the generated code is status-derived.

**Impact:** The web client cannot reliably attach a message to a field, show a
typed conflict state, or localize domain errors without parsing English text.
Support staff also have to correlate a request ID manually; the response does
not set a separate `X-Request-Id` header.

**Expected behavior:** Every failure has a stable machine code, a safe user
message, optional structured details, and a request ID that is available in both
the body and response headers.

**Recommendation:** Introduce a backward-compatible error envelope with
`success: false`, `details?: Record<string, unknown>`, and a documented code
catalog. Preserve the current fields during migration and add contract tests for
validation, authorization, conflict, rate-limit, and unexpected errors.

**Status:** Open; design before implementation.

### AUD-004 — P1: account-mail delivery failures have no operator signal

**Category:** Background jobs / observability  
**Location:** `apps/api/src/auth/auth-mail.service.ts:120-228`  
**Evidence:** Delivery retries up to eight attempts and persists `failedAt` after
the final failure. The polling catch logs only
`Account email dispatch temporarily unavailable`; no metric, alert, readiness
degradation, admin count, or incident event is emitted for permanently failed
rows.

**Impact:** Invitations and password resets can remain undelivered while the API
continues to report healthy. The user sees a generic failure only if they happen
to discover it in the UI or mailbox.

**Expected behavior:** A provider outage creates an actionable operator signal,
with safe metadata and a retry/dead-letter count, without logging tokens or email
contents.

**Recommendation:** Add structured counters and a bounded alert for failed rows,
surface the count in an admin health view, and retain the existing token-redaction
rules. Add tests for retry exhaustion and alert suppression.

**Status:** Open.

**Update (2026-10-09):** The delivery worker now claims rows in a short
transaction, performs provider I/O outside the transaction, records a safe
provider/attempt/reason signal, and keeps retry state bounded. Metrics and
alerting for terminal failures remain follow-up work.

### AUD-005 — P1: security baseline depends on an unverified proxy

**Category:** Security / HTTP hardening  
**Location:** `apps/api/src/main.ts:9-16`,
`apps/api/src/config/http-application.ts:5-17`  
**Evidence:** The Nest/Fastify bootstrap configures versioning, validation,
multipart, and shutdown hooks, but no application-level CORS allowlist, security
headers, or explicit trusted-proxy policy was found. Only two sensitive
controllers set a `Referrer-Policy` header locally.

**Impact:** If the production proxy is misconfigured or bypassed, browser-origin
access and headers such as CSP, HSTS, frame protection, and content-type
sniffing protection are not guaranteed. This is especially risky for invitation,
session, export, and admin surfaces.

**Expected behavior:** The production boundary has a documented, tested CORS
allowlist and security-header policy, with the proxy and API responsibilities
explicitly assigned.

**Recommendation:** Decide whether headers/CORS are owned by the API or edge,
then enforce the policy in one place and add an automated header smoke test.
Do not use a wildcard origin with credentials.

**Status:** Open / needs deployment verification.

### AUD-006 — P1: CI does not gate worker behavior or dependency security

**Category:** CI / release assurance  
**Location:** `.github/workflows/ci.yml:105-127`  
**Evidence:** CI runs API integration tests and the monorepo `pnpm build`, but
there is no explicit worker unit/integration test step, dependency audit, image
scan, or deployment smoke test. The build step is skipped when integration fails.

**Impact:** A worker-only regression, queue retry regression, or known vulnerable
dependency can reach the release candidate without a dedicated gate.

**Expected behavior:** API, worker, and web have explicit quality gates, and
security/dependency checks are visible in the required status checks.

**Recommendation:** Add worker tests to the required CI job, run a reproducible
lockfile-based dependency audit, and publish the exact required checks in branch
protection documentation. Keep network-dependent scans tolerant of registry
outages but never silently green.

### AUD-007 — P2: readiness reporting can be misleading during optional-provider failures

**Category:** Health checks / operations  
**Location:** `apps/api/src/health/readiness.controller.ts:22-63`  
**Evidence:** Readiness checks Postgres and Redis with `Promise.race`, but the
underlying promise is not cancelled when the deadline wins. Optional email status
only checks Brevo variables and does not recognize the local `MAILPIT_URL` path.

**Impact:** A slow dependency can continue consuming a pool/socket after the
request is marked failed. A local or staged environment using Mailpit is reported
as having email unconfigured even though the configured mail path is usable.

**Expected behavior:** Timeouts cancel or isolate the underlying work, and health
status reflects the selected provider path with explicit production requirements.

**Recommendation:** Use an abortable query/ping boundary or a pool-level timeout,
and report `MAILPIT_URL` as configured only outside production. Add readiness
contract tests for Brevo, Mailpit, and timeout cases.

**Status:** Open.

**Update (2026-10-09):** Readiness now reports API pool utilization and treats
Mailpit as configured in non-production while preserving Brevo checks for
production. The underlying Postgres/Redis probe is still bounded by a deadline;
full cancellation remains follow-up work.

### AUD-008 — P2: user-facing fallback errors remain inconsistent

**Category:** Frontend UX / localization  
**Locations:** `apps/web/src/app/(app)/director/overview/page.tsx:331-344`,
`apps/web/src/components/prospector/action-history-drawer.tsx:307-320`,
`apps/web/src/app/(app)/manager/team/page.tsx:708-726`, and additional
assignment/user/campaign pages found by repository search  
**Evidence:** Several screens use generic English fallbacks such as “Something
went wrong. Please try again.” or “We could not load this team. Please try
again.” Some pages translate their errors with the `l(en, fr)` helper, while
others do not.

**Impact:** Users cannot tell whether they should reload, sign in again, narrow a
scope, or retry a provider operation. French users see English in failure paths,
and support cannot consistently correlate a request ID.

**Expected behavior:** Shared error mapping produces a contextual, localized
message, retry action, and request reference without leaking server internals.

**Recommendation:** Centralize status/code mapping in the web API client, add
French/English translations for every domain code, and remove page-specific
generic fallbacks after contract coverage exists.

**Status:** Open.

### AUD-009 — P2: operational documentation is stale or explicitly incomplete

**Category:** Documentation / release readiness  
**Locations:** `README.md:3-6`, `README.md:151-154`,
`docs/backend/BACKEND_AUDIT_2026-09-30.md:58-96`,
`docs/operations/DEPLOYMENT.md`, `docs/operations/BACKUP_RESTORE.md`  
**Evidence:** The prior backend audit documents 85 applied migrations, while the
current repository has 92. It also records unverified Brevo, R2, SSO, provider,
RLS, load, and restore gates. Deployment documentation still says the hosting
provider is undecided. Backup/restore documentation says production scheduling,
off-account retention, RPO/RTO, and a real object-store rehearsal are pending.

**Impact:** Operators can follow outdated counts or assume a checkpoint is current
when it is not. Incident response and release approval lack one authoritative
status page.

**Expected behavior:** Every audit and runbook has a date, commit, environment,
owner, and explicit pass/fail/blocked state.

**Recommendation:** Link this audit from the docs index, archive superseded
snapshots, and update migration/provider/backup evidence after each staging
rehearsal.

**Status:** Open.

### AUD-010 — P3: test output contains avoidable warnings and simulated error noise

**Category:** Developer experience / test hygiene  
**Evidence:** Local Vitest runs pass but emit Vite config-loader warnings,
jsdom canvas/navigation warnings, and expected error logs from simulated Redis,
queue, and idempotency failures.

**Impact:** Important regressions are harder to spot in CI logs and local review.

**Recommendation:** Suppress only known, asserted warnings at the test boundary;
keep unexpected errors visible. Track the pg query-concurrency deprecation seen in
integration logs as a separate dependency/code cleanup.

**Status:** Open; non-blocking.

## Security observations that passed

- Environment files are ignored and only `.env.example` files are tracked.
- JWT secrets are required and must be at least 32 characters.
- MFA encryption keys are validated as 32-byte hexadecimal values.
- Global validation uses `whitelist` and `forbidNonWhitelisted`.
- Invitation tokens are kept in URL fragments and are not logged by the mail
  service; mail payloads are encrypted in the outbox.
- Audit metadata rejects sensitive token/password/cookie keys and validates JSON
  depth/types.
- The API integration suite includes tenant RLS, authorization, invitation
  security, controlled export, reservation, and collision scenarios.

These controls still need staging/provider verification before being treated as
production evidence.

## Controlled remediation protocol

No production remediation was applied as part of this audit. The next change
should follow this order:

1. approve the backlog item and owner;
2. write a focused design/test plan;
3. implement on `dev-v2` only;
4. run the affected unit, integration, build, and security checks;
5. review the diff and update this report with evidence;
6. open a pull request to protected `main` only after the required CI checks are
   green.

The current audit report itself is documentation only; it does not alter runtime
behavior or production infrastructure.
