## Execution order

1. TR-100 reconciles main, frontend-dev, the administration branch and the current dirty working tree; repair the verified audit-test failures and establish a green baseline.
2. TR-101/TR-108/TR-109 lock role/contract/security boundaries; TR-102 → TR-103 → TR-104 completes membership and database isolation.
3. Complete backend administration and prospect/consent/import/assignment/action/collision workflows in dependency order. TR-130 supplies the durable event substrate.
4. Complete reports/exports/audit/privacy and operational release evidence. Backend readiness is more than endpoint existence.
5. Complete P0 frontend flows against those contracts, then TR-154 verifies the dossier MVP acceptance conditions.
6. P1 completes remaining designed workspaces and workflows; P2 adds platform/SSO/optimization expansion. Neither phase is silently discarded.

Dependencies are explicit in GitHub issues and backlog.json. Source priorities and planned phases differ intentionally where the supplied documents conflict. No delivery dates or effort estimates are asserted before baseline reconciliation. Large work packages are delivered through multiple logical PRs, never one all-project commit.

## Publication and completion policy

Push each verified logical implementation on an issue-linked branch and open/update its PR. Keep schema, migration and regression tests together. Reference the ticket for partial delivery; close it only when all acceptance criteria pass. Merging and production deployment are separate actions.

This planning PR changes documentation only. The existing uncommitted application changes remain in the original worktree. The recorded four failing API tests belong to that assessed working tree; this PR does not claim to fix or release it.
